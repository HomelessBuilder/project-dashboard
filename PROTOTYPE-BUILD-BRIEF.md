## Objective

Build a working v1 Diego can actually open and evaluate. No backend, no
database, no server process to keep alive. Same pattern already proven by
`~/claude-journal-private/devlog.html`: a single HTML file, styled, that
turns existing markdown into a readable view. The difference here is *when*
the data gets read — bake it in at generation time rather than fetching it
at runtime (see Technical Approach below). That sidesteps the CORS problem
`devlog.html` has and means no local server is needed to view the result.

## Scope for This Build

- One project card per active entry in `~/CLAUDE.md`'s Active Projects list
- Per card: current status, what's in progress, next action, open
  questions/blockers — pulled from `~/claude-journal-private/CURRENT.md`
- Regenerated on demand: a Claude Code session in this directory reads the
  source files fresh and writes a new static HTML file each time Diego wants
  an updated view
- Ugly is fine. Clarity over polish, per VISION.md's own stated bar for v1.

## Explicitly Out of Scope for This Build

- No database, no write-back to any source file, no live-updating/polling
- No auth — this is a local single-user file
- No framework, no build step, no npm dependency
- No modification of `claude-journal-private` files, ever (standing rule,
  already in this project's CLAUDE.md)

## Data Sources (read-only)

- `~/claude-journal-private/CURRENT.md` — primary source, one block per
  project with consistent `**Status:**` / `**In progress:**` /
  `**Next action:**` / `**Open questions/blockers:**` fields
- `~/CLAUDE.md` — active project list, for names/paths/descriptions if a
  project has no CURRENT.md block yet
- `~/monitor/reports/CONCERNS.md` if present — see "cheap v1 addition" below
- Do not read individual project CLAUDE.md files for v1 — CURRENT.md already
  has what's needed; pulling more sources now adds parsing surface for
  marginal value

## Technical Approach

1. Write a small generator step (can be the Claude Code session itself doing
   the read-and-template, no separate script required for v1) that parses
   `CURRENT.md`'s block format the same way `devlog.html`'s `parseDevlog()`
   parses `DEVLOG.md` — same idea, different field shape.
2. Inline the parsed data directly into the HTML as rendered cards — not as
   a JS `fetch()` call. This is the key difference from `devlog.html`'s
   pattern and it's deliberate: it's what lets this open via plain
   double-click with zero server.
3. Reuse `devlog.html`'s CSS variables and card styling for visual
   consistency across the ecosystem's tools (`--bg`, `--surface`, `--accent`,
   etc. — grep that file for the full palette).
4. Output file: `dashboard.html` in this directory, regenerated by
   re-running the same session/prompt each time a fresh view is wanted.

## Cheap v1 Addition Worth Including

VISION.md lists "surface maintenance gaps automatically" as future scope,
not v1. It's actually nearly free right now: `~/monitor` already runs on
cron and already computes exactly this — silence >48h, drift, unexpected
files — into `~/monitor/reports/CONCERNS.md`. Rendering the latest
concerns file as a small "Attention" section at the top of the dashboard is
one more read-only file read, no new logic to invent, and it turns two
already-working tools into one better one. Recommended for v1, not v2.

## Evaluation Criteria

Diego opens `dashboard.html` in a browser with zero setup and can answer,
for every active project, in under 30 seconds: what's the status, what's
next, what's blocked. If that's true, the prototype has done its job —
everything past that is refinement.

## Backend Roadmap (Do Not Build Now — Plan Only)

**Update, 2026-07-27:** Item 1 below is done. devlog-engine landed, became
the sole system of record (dual-write to `CURRENT.md`/`DEVLOG.md` dropped
2026-07-23), and `generate.py` was swapped over to its CLI the same day
this note was added — exactly the swap this section predicted, on the
sequencing it recommended (data-source swap only, card design unchanged).
See `CLAUDE.md` for the current architecture. Item 2 (ai-dev-platform
serving this live via MCP) is still future — that project remains
pre-build.

The prototype intentionally has no backend. But two backends are *already
planned elsewhere in the ecosystem* for exactly this kind of data, and this
project's own docs already name it as their eventual consumer — don't
invent a third:

1. **devlog-engine** (`~/devlog-engine`, planning phase) will eventually
   replace the flat-file `CURRENT.md`/`DEVLOG.md` pair with local MySQL plus
   a query layer. When that lands, this dashboard's generator step swaps
   "parse markdown" for "query the database" — the rendered output and card
   design don't need to change, only the data-fetch step. Do not design
   against a MySQL schema now; devlog-engine's own principle (stated in its
   VISION.md) is schema-from-observed-friction, not speculation — nothing
   to do here until that schema exists.
2. **ai-dev-platform** (`~/ai-dev-platform`, pre-build) already names this
   project as "the visual layer this platform extends with interactivity"
   in both its own CLAUDE.md and VISION.md. That platform's Phase 5 builds
   a read-only local MCP server exposing `CURRENT.md`/`DEVLOG.md`/CLAUDE.md
   files on demand. When that exists, the natural "live" version of this
   dashboard is served *through* ai-dev-platform's FastAPI backend querying
   MCP, not a bespoke server built inside this repo. That keeps one backend
   for "AI/UI needs current project state," not two competing ones.

**Sequencing implication:** this prototype's job is to prove out the *card
design and information shape* — what fields actually matter at a glance,
what's cluttered, what's missing. That's exactly the design process
VISION.md already describes. The migration to a live-updating version
should follow the same staged automation ladder devlog-engine established
for logging (manual → hook-prompted → hook-drafted → autonomous): this
prototype is "manual regenerate," the next step is a hook that regenerates
it automatically on a trigger (e.g. after `/journal` sweeps), and only after
that is trusted does it move to querying a live backend instead of files.
Don't jump stages.

generated `dashboard.html` ever gets committed, it bakes a snapshot of that
content into git history. Two things to resolve before that happens, not
after:
- Confirm `project-dashboard`'s GitHub repo is private (unconfirmed as of
  this brief — `gh` wasn't authenticated when checked). If it's public,
  this is the same class of issue IDEA-010 already found and fixed for
  `claude-journal` — don't repeat it here.
- Add a `.gitignore` for the generated `dashboard.html` output (there is
  currently none in this repo) unless Diego confirms he wants generated
  snapshots committed as a history of "state at a glance over time." Ask
  rather than assume either way.
